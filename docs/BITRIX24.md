# Битрикс24: план пилотной интеграции

Статус: этап 1 реализован локально; проверка на настоящем портале ещё не выполнена.
Портал пилота: `https://is4business.bitrix24.ru`; администратор подтвердил права и подписку.
Привязка аккаунтов, задачи и синхронизация календаря пока не реализованы.
Изменения разрабатываются отдельными коммитами без публикации и без пуша в main.

## Что нужно получить от администратора Б24

Сведения о портале, правах и подписке получены. Для следующих этапов нужны:

- Точный HTTPS-адрес портала, включая собственный домен, если он используется.
- Подтверждение прав на создание серверного локального приложения.
- Подтверждение действующего доступа к REST API (подписка Маркетплейс или пробный период).
- Два сотрудника для пилота: администратор и обычный сотрудник. Для каждого — ID Б24,
  существующий ник Квазара, наличие личного мобильного номера в профиле Б24.
  Пароли, реальные номера телефонов и выгрузка справочника на подготовительном этапе не нужны.
- Рабочая Звезда Квазара и тестовая комната, к которой будет подключена компания.

Перед этапом задач:

- ID тестового проекта/группы Б24, если задачи должны попадать в проект.
- Список обязательных пользовательских полей задач и их допустимые значения, если такие поля есть.
- Подтверждение, что обычный тестовый сотрудник может назначать задачи выбранному исполнителю.

Перед этапом календаря:

- Какой календарь использовать в пилоте: личный организатора или тестовый календарь группы.
- Для календаря группы — ID группы; ID секции календаря можно получить через API.
- Часовой пояс компании и правило доступа к выбранной комнате.
- Для первого пилота — одиночные встречи с заданным временем, без повторяющихся серий.

## Настройка приложения — после размещения обработчиков

Для пилота подготовлено отдельное размещение в `/opt/quazar-bitrix24`, compose-проект
`quazar-bitrix24-pilot`, отдельные база, медиа и секреты. Из production не копируются
аккаунты, переписка, ключи или `.env.prod`. Единственное дополнение к host-nginx —
маршрут `/bitrix24-pilot/`; перед reload выполняется nginx -t, прежний конфиг сохраняется.
Сборка из feature-ветки запускается вручную workflow `deploy.yml`; production job
для feature-ветки отключён. Код main и работающие контейнеры production не обновляются.

Поля формы «Разработчикам → Локальное приложение → Серверное» для пилота:

- Название пункта меню: «Квазар».
- Путь первоначальной установки: `https://quazar-msg.ru/bitrix24-pilot/api/integrations/bitrix24/install`.
- Путь обработчика: `https://quazar-msg.ru/bitrix24-pilot/api/integrations/bitrix24/launch`.
- Приложение само завершает установку: включено.
- Права первого пилота: пользователи `user` для телефона и почты, задачи `task`
  для выбранных методов REST v2, календарь `calendar`. Право `placement` добавляется
  при реализации вида календаря `CALENDAR_GRIDVIEW`.

Проверка доступности: `https://quazar-msg.ru/bitrix24-pilot/healthz`.
Пока ключи приложения не заданы, обработчики отвечают 404 «Интеграция Б24 ещё не настроена» —
это ожидаемо. После сохранения формы Б24 выдаст код и ключ приложения. Их можно сохранить
в GitHub Actions secrets репозитория: `BITRIX24_PILOT_CLIENT_ID` и `BITRIX24_PILOT_CLIENT_SECRET`.
Повторный ручной запуск `deploy.yml` на ветке `feature/bitrix24-pilot` перенесёт их в защищённое
окружение только пилота. Первую установку затем нужно открыть ещё раз. Секреты не присылаются в чат.
Если secrets пусты, повторная выкладка сохраняет прежние настройки, включая Fernet-ключ.

У приложения будут собственные client_id и client_secret. Их настраиваем на сервере
в защищённом окружении; секрет, OAuth-токены и секретные URL вебхуков не помещаем
в чат, репозиторий, логи, URL переходов или браузерное постоянное хранилище.
На этом этапе входящий вебхук создавать не нужно: действия выполняются в контексте сотрудника.
member_id портала и ID текущего сотрудника получаем при проверенной установке/запуске и через API.

### Серверные настройки этапа 1

В защищённом окружении бэкенда задаются:

```dotenv
BITRIX24_PORTAL_URL=https://is4business.bitrix24.ru
BITRIX24_CLIENT_ID=
BITRIX24_CLIENT_SECRET=
BITRIX24_TOKEN_KEY=
```

`BITRIX24_TOKEN_KEY` — отдельный постоянный Fernet-ключ. Генерация в окружении бэкенда:

```sh
python -c 'from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())'
```

Полученный ключ сохраняется только в защищённом окружении. Замена ключа делает сохранённые
OAuth-токены нечитаемыми: не генерировать новый при каждом запуске или обновлении.
После получения client_id/client_secret в форме Б24 администратор сохраняет их в окружении
и повторно открывает установку. До задания всех четырёх настроек обработчики отвечают 404.

Входные POST-запросы запуска проверяются обменом refresh_token на сервере OAuth Б24
с нашим client_secret; затем проверяются портал, код приложения, текущий активный сотрудник
и (при установке) права администратора. APPLICATION_TOKEN фиксируется хэшем после этой
проверки. Данные AUTH_ID, user_id и произвольные REST endpoint из формы не используются.
Установка с мастером ожидает плоские параметры REFRESH_ID/APPLICATION_TOKEN/member_id,
не callback события ONAPPINSTALL с вложенным объектом auth.

После запуска происходит переход в `/bitrix24.html` с одноразовым кодом на 60 секунд.
Код сразу удаляется из адресной строки и обменивается один раз. OAuth-токены остаются
в зашифрованном виде на сервере, cookies и localStorage для запуска не требуются.
На этапе 1 это только проверенный контекст Б24; сессия Квазара ещё не выдаётся.

Разрешение фрейма находится в `web/nginx.spa.conf`: только `/bitrix24.html` и только
портал пилота. При смене портала нужно согласованно изменить это разрешение и настройки
бэкенда. Обычный index.html запрещён во фреймах. Конфигурация edge-nginx содержит
исключение для этой единственной страницы; при использовании другого внешнего proxy
его заголовки также не должны добавлять X-Frame-Options DENY к `/bitrix24.html`.
Vite dev/preview по-прежнему запрещает фреймы: для проверки в реальном Б24 используйте
production-сборку с подготовленным nginx. Простое открытие файла не подтверждает запуск.

Тесты:

```sh
cd backend
TEST_DATABASE_URL=postgresql+asyncpg://USER@localhost:PORT/DB .venv/bin/python -B -m unittest tests.test_bitrix24
```

Тесты используют отдельную схему quazar_test, которую пересоздают; запускать только
на специально выделенной тестовой базе. Внешние HTTP-вызовы Б24 заменены тестовым transport.
Клиентские проверки: `npm test --prefix web -- src/bitrix24`; сборка: `npm run build --prefix web`.

## Отдельные этапы и коммиты

### 0. Подготовка

Этот документ: входные данные, границы пилота и критерии приёмки.

### 1. Встройка и проверенный контекст Б24

Серверные обработчики установки и запуска, настройки подключения, отдельный встроенный
маршрут React и разрешение фрейма только для подключённого портала.
Проверка происхождения запроса и OAuth-контекста; домен/ID из POST сами по себе не являются
доказательством личности. REST endpoint строится только из доверенной конфигурации портала.
Встроенная сессия не должна зависеть от разрешения сторонних cookies.

Приёмка: администратор устанавливает приложение; обычный сотрудник открывает Квазар из меню;
чужой портал и поддельный запуск отклоняются; секреты не попадают в клиент.
Микрофон, камера, демонстрация экрана, переход в другой раздел Б24 и возврат проверяются
на настоящем портале в браузере и клиенте Б24. При ограничениях родительского фрейма
согласуется переход звонка в отдельное окно до обещания полной работы звонков внутри Б24.

### 2. Безопасная привязка существующего аккаунта

Связь `(member_id портала, ID сотрудника) → аккаунт Квазара` и корпоративная почта
в записи связи. Активный сотрудник с подходящим мобильным номером подтверждает
привязку действующей авторизацией Квазара; совпадение номера не выдаёт доступ.
Личная почта восстановления и ключи переписки не заменяются корпоративными данными.
Импорт новых аккаунтов с предпросмотром и подтверждением телефона — отдельное расширение,
не условие пилота с существующими пользователями.

Приёмка: нельзя связать чужой аккаунт, подменить сотрудника или смешать порталы;
повторная привязка обрабатывается явно; отвязка отзывает корпоративный вход.
Доступ к Звезде и комнате проверяется независимо от факта входа в Б24.

### 3. Задача из сообщения

Действие у сообщения, редактируемая форма, исполнитель, срок, проект и необходимые
пользовательские поля. Явное подтверждение передачи выбранного текста в Б24.
Задача создаётся от связанного сотрудника с его правами, сохраняется связь и ссылка.

Приёмка: отказ Б24 отображается понятно; повторный клик не создаёт дубль;
после сетевого таймаута результат проверяется до повторного создания;
зашифрованный текст передаётся только по явному действию пользователя.

### 4. Встреча с подтверждённой бронью

Единая форма встречи, проверка прав на комнату, защита от конкурирующего бронирования,
создание события Б24 и связанной брони Квазара. Общей транзакции с Б24 нет:
нужны состояния операции, временное удержание комнаты и компенсация при ошибках.
Успех показывается только после подтверждения обеих записей. Неопределённый результат
REST-запроса сверяется до освобождения комнаты или повторного создания события.
Перенос, отмена, повторы событий и периодическая сверка входят в этап синхронизации.

Приёмка: два сотрудника не бронируют одно время; сбои не оставляют ложного подтверждения;
перенос и отмена согласуют обе системы; часовые пояса сохраняются.
Текущие ограничения Квазара: до 8 часов, не дальше 60 дней. Для пилота сохраняются.

## Порядок проверки и публикации

Для каждого этапа — отдельный коммит и тесты соответствующих границ доверия/сбоев.
Установка и действия в реальном Б24 требуют доступных HTTPS-обработчиков.
До отдельного решения о тестовом размещении/выкладке код остаётся локально;
публикация в Маркете в пилот не входит. Автоматическое создание задач, встреч,
приглашений и изменение сотрудников на рабочем портале при разработке не выполняются.
