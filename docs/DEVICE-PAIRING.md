# Вход через другое устройство

Функция доступна в общем веб-интерфейсе: браузер, PWA и десктопные приложения Windows/macOS. Отдельное нативное мобильное приложение и passkeys в этот этап не входят.

## Как пользоваться

**Телефон подтверждает вход на компьютере.** На новом устройстве выберите «Войти по QR-коду». На уже авторизованном телефоне откройте Настройки → Устройства → Подключить по QR или коду. Отсканируйте QR встроенным сканером или введите показанный одноразовый код. Сравните код на обоих экранах и разрешите вход. На новом устройстве подтвердите «Войти как …».

**Компьютер подключает телефон.** Настройки → Устройства → Подключить телефон. Откройте QR камерой телефона: ссылка ведёт на страницу подключения Quazar. Сравните коды, разрешите вход на компьютере и подтвердите аккаунт на телефоне. Если телефон уже авторизован, сначала потребуется явно выйти: автоматической смены аккаунта нет.

QR действует две минуты; после одобрения даётся одна минута на завершение. Закрытие страницы принимающего устройства отменяет незавершённое подключение. Закрытие окна подтверждения после одобрения не отменяет разрешение до истечения его срока. Если QR больше не действует, создайте новый.

В разделе «Устройства» можно завершить отдельный сеанс или все остальные. Текущий сеанс при массовом завершении получает новый токен. Старые сеансы попадают в список после первого обращения к обновлённому серверу; «Завершить остальные» также блокирует ещё не зарегистрированные старые токены. Доступ по HTTP прекращается сразу после фиксации отзыва; локальные WebSocket-соединения закрываются сразу, соединения другого серверного процесса проверяют отзыв при событиях и не реже одного раза в 30 секунд. Клиент перепроверяет сеанс и выходит.

## Переписка и ограничения

Текущее устройство передаёт ключ личной переписки только если его локальный ключ совпадает с ключом аккаунта и доступен для экспорта. Вместе с ним передаются доступные архивные ключи, явно связанные с этим же аккаунтом. Очень старые ключи без информации о владельце, ключи другого аккаунта и неэкспортируемые ключи остаются на исходном устройстве. Поэтому доступность всей старой истории не гарантируется.

Если перенос текущего ключа невозможен, подтверждающий пользователь должен отдельно согласиться на вход без переноса переписки. Затем на новом устройстве требуется обычное восстановление ключей из резервной копии. Подключение не заменяет ключ аккаунта на сервере и не подтверждает телефон у старого аккаунта.

Завершение сеанса не удаляет скачанные сообщения и локальные ключи с чужого устройства. Подключённый сеанс ограничен сроком исходного сеанса и обычным сроком JWT: цепочка подключений не продлевает доступ бесконечно.

## Протокол и защита

- Принимающее и подтверждающее устройства создают временные пары X25519 в памяти. Ключи переписки упакованы в аутентифицированный NaCl box (XSalsa20-Poly1305, случайный nonce 24 байта). Открытые seed и приватные временные ключи не отправляются серверу.
- SHA-256 контекста связывает ID запроса, оба временных публичных ключа, ID аккаунта, текущий публичный ключ переписки и название устройства. Пользователь сравнивает первые 64 бита хеша на двух экранах. Клиенты фиксируют контекст после выбора аккаунта и отвергают его изменение.
- QR содержит публичный ключ и ID; приглашение также содержит одноразовый секрет приглашения. JWT и отдельный 256-битный секрет получения результата в QR не попадают. Данные ссылки находятся во фрагменте URL, который страница удаляет после чтения. Сканер принимает только собственный origin и путь `/connect`.
- Сервер хранит хеши кодов и секретов. Для коротких кодов, создания и принятия запросов есть ограничения частоты в PostgreSQL, общие для процессов. Чувствительные ответы имеют `Cache-Control: no-store`.
- Выдача токена требует одобрения точным исходным сеансом и приватного секрета принимающего устройства. Повторное получение после потери ответа возвращает тот же сеанс, пока разрешение действительно. Истечение, отмена, блокировка, отзыв исходного сеанса, смена глобальной эпохи безопасности, JWT-ключа или ключа переписки блокируют выдачу.
- Перед активацией клиент проверяет аккаунт и актуальный публичный ключ через новый токен, затем атомарно импортирует ключи. Ошибка закрывает новый сеанс. Параллельные входы в разных вкладках координируются через Web Locks там, где API доступен; изменения сохранённого аккаунта дополнительно проверяются.
- Это не защита от фишинга с пересылкой чужого настоящего QR-кода: подтверждайте только своё устройство на официальном сайте/в приложении и сверяйте оба экрана. Вредоносный код в самом origin также выходит за гарантии протокола. Общая модель: [e2e-threat-model.md](e2e-threat-model.md).

Новые таблицы `device_sessions`, `device_pairings`, `device_pair_limits` создаются штатным `Base.metadata.create_all` при старте сервера. Новых переменных окружения не требуется. HTTPS и корректный доверенный reverse proxy обязательны для production. Периодическая задача очищает просроченные зашифрованные пакеты, старые запросы и счётчики; записи отозванных сеансов сохраняются до истечения JWT.

## Проверки

Backend: `python -B -m unittest tests.test_device_pairing` из `backend`, с `TEST_DATABASE_URL` на тестовую PostgreSQL. Suite пересоздаёт схему `quazar_test`; не запускайте несколько таких suite одновременно.

Web: `npm test` и `npm run build` из `web`.

Сквозная проверка: сначала соберите `web` и установите зависимости `desktop`, затем из корня запустите `backend/.venv/bin/python -B desktop/test/run-device-pairing.py`. `TEST_DATABASE_URL` должен указывать на локальную PostgreSQL с правом создания временной БД. Harness создаёт и удаляет отдельную БД, синтетический аккаунт и четыре изолированных профиля Chromium; внешние запросы заблокированы. Проверяет код, QR в обе стороны, реальное декодирование отображённого QR, совпадение перенесённого seed, разные сеансы и их отзыв. На Linux нужен `xvfb-run -a`. В CI эти проверки обязательны перед десктопной сборкой.
