# Вход через другое устройство

Вход по QR доступен в общем веб-интерфейсе: браузер, PWA и десктопные приложения Windows/macOS. Нативное мобильное приложение умеет передавать и получать ключи переписки и подтверждать вход по одноразовому коду (без камеры и QR). Passkeys в этот этап не входят.

## Как пользоваться

**Телефон подтверждает вход на компьютере.** На новом устройстве выберите «Войти по QR-коду». На уже авторизованном телефоне откройте Настройки → Безопасность → Подключить по QR или коду. Отсканируйте QR встроенным сканером или введите показанный одноразовый код. Сравните код на обоих экранах и разрешите вход. На новом устройстве подтвердите «Войти как …».

**Компьютер подключает телефон.** Настройки → Безопасность → Подключить телефон. Откройте QR камерой телефона: ссылка ведёт на страницу подключения Quazar. Сравните коды, разрешите вход на компьютере и подтвердите аккаунт на телефоне. Если телефон уже авторизован, сначала потребуется явно выйти: автоматической смены аккаунта нет.

QR действует две минуты; после одобрения даётся одна минута на завершение. Закрытие страницы принимающего устройства отменяет незавершённое подключение. Закрытие окна подтверждения после одобрения не отменяет разрешение до истечения его срока. Если QR больше не действует, создайте новый.

В разделе «Устройства» можно завершить отдельный сеанс или все остальные. Текущий сеанс при массовом завершении получает новый токен. Старые сеансы попадают в список после первого обращения к обновлённому серверу; «Завершить остальные» также блокирует ещё не зарегистрированные старые токены. Доступ по HTTP прекращается сразу после фиксации отзыва; локальные WebSocket-соединения закрываются сразу, соединения другого серверного процесса проверяют отзыв при событиях и не реже одного раза в 30 секунд. Клиент перепроверяет сеанс и выходит.

**Ключи переписки на устройство, где уже вошли.** Если устройство вошло в аккаунт (звонком, паролем, через Яндекс), но ключа переписки на нём нет, выходить не нужно. В окне «Восстановите ключи шифрования» нажмите «Получить ключи с другого устройства» — появятся QR и одноразовый код. На других открытых устройствах этого аккаунта (сайт, PWA, приложение для компьютера) сразу всплывёт предложение «… просит ключи шифрования» → «Передать ключи». Иначе: отсканировать QR камерой телефона, ввести код в Настройки → Безопасность → Подключить по QR или коду, а в мобильном приложении — Профиль → Ключи шифрования → «Передать ключи на другое устройство». Сравните код на обоих экранах и подтвердите; ключи сохранятся сами. Пароль резервной копии не нужен, сеанс не меняется.

Запрос ключей действует пять минут. Занять его может только другое устройство того же аккаунта; когда его заняли или отменили, предложение пропадает с остальных экранов. Подтверждение без передачи ключа невозможно — передавать должно устройство, где переписка читается.

## Переписка и ограничения

Текущее устройство передаёт ключ личной переписки только если его локальный ключ совпадает с ключом аккаунта и доступен для экспорта. Вместе с ним передаются доступные архивные ключи, явно связанные с этим же аккаунтом. Очень старые ключи без информации о владельце, ключи другого аккаунта и неэкспортируемые ключи остаются на исходном устройстве. Поэтому доступность всей старой истории не гарантируется.

Если перенос текущего ключа невозможен, подтверждающий пользователь должен отдельно согласиться на вход без переноса переписки. Затем на новом устройстве требуется обычное восстановление ключей из резервной копии. Подключение не заменяет ключ аккаунта на сервере и не подтверждает телефон у старого аккаунта.

Завершение сеанса с другого устройства не удаляет локальные ключи с того устройства. Чтобы стереть их, выходите на нём самом с отметкой «Удалить ключи шифрования и черновики с этого устройства» (веб и приложение для компьютера): стираются текущий и архивные ключи этого аккаунта, его зашифрованные черновики с их ключом и список проверенных ключей собеседников; ключи других аккаунтов в этом браузере остаются. Если стереть не удалось, выход не выполняется. Подключённый сеанс ограничен сроком исходного сеанса и обычным сроком JWT: цепочка подключений не продлевает доступ бесконечно.

## Протокол и защита

- Принимающее и подтверждающее устройства создают временные пары X25519 в памяти. Ключи переписки упакованы в аутентифицированный NaCl box (XSalsa20-Poly1305, случайный nonce 24 байта). Открытые seed и приватные временные ключи не отправляются серверу.
- SHA-256 контекста связывает ID запроса, оба временных публичных ключа, ID аккаунта, текущий публичный ключ переписки и название устройства. Пользователь сравнивает первые 64 бита хеша на двух экранах. Клиенты фиксируют контекст после выбора аккаунта и отвергают его изменение.
- QR содержит публичный ключ и ID; приглашение также содержит одноразовый секрет приглашения. JWT и отдельный 256-битный секрет получения результата в QR не попадают. Данные ссылки находятся во фрагменте URL, который страница удаляет после чтения. Сканер принимает только собственный origin и путь `/connect`.
- Сервер хранит хеши кодов и секретов. Для коротких кодов, создания и принятия запросов есть ограничения частоты в PostgreSQL, общие для процессов. Чувствительные ответы имеют `Cache-Control: no-store`.
- Запрос ключей (`kind = "keys"`, `POST /auth/device-pairing/key-requests`) создаёт только авторизованное устройство; он привязан к его сеансу и аккаунту. Чужой аккаунт получает на такой код «не найден», тот же сеанс не может подтвердить себя сам. Забрать пакет (`POST …/key-requests/{id}/consume`) может только запросивший сеанс с приватным секретом; новый токен такой запрос не выдаёт. Другим устройствам аккаунта по WebSocket уходят `device_key_request` (ID, публичный ключ устройства и его название — без кода и секрета) и `device_key_request_closed`.
- Отметка ключа: после каждой проверки ключей устройство вызывает `PUT /auth/devices/current/key` с публичным ключом, если он совпадает с ключом аккаунта, или `null`. Сервер сохраняет его в `device_sessions.e2e_public_key` (чужой ключ сохраняется как `null`), а `GET /auth/devices` отдаёт `has_account_key`: `true` — ключ совпадает с текущим ключом аккаунта, `false` — устройство сообщило, что ключа нет, или ключ аккаунта с тех пор сменили, `null` — устройство не сообщало (старая версия). Справка о ключах по этой отметке подсказывает, где взять ключ. Секретов отметка не раскрывает: публичный ключ аккаунта и так виден собеседникам.
- Мобильное приложение реализует тот же протокол на `@noble` (X25519 + XSalsa20-Poly1305, SHA-256): пакеты и коды сравнения совместимы с веб-версией в обе стороны. Архивные ключи телефон не передаёт — они не привязаны к аккаунту.
- Выдача токена требует одобрения точным исходным сеансом и приватного секрета принимающего устройства. Повторное получение после потери ответа возвращает тот же сеанс, пока разрешение действительно. Истечение, отмена, блокировка, отзыв исходного сеанса, смена глобальной эпохи безопасности, JWT-ключа или ключа переписки блокируют выдачу.
- Перед активацией клиент проверяет аккаунт и актуальный публичный ключ через новый токен, затем атомарно импортирует ключи. Ошибка закрывает новый сеанс. Параллельные входы в разных вкладках координируются через Web Locks там, где API доступен; изменения сохранённого аккаунта дополнительно проверяются.
- Это не защита от фишинга с пересылкой чужого настоящего QR-кода: подтверждайте только своё устройство на официальном сайте/в приложении и сверяйте оба экрана. Вредоносный код в самом origin также выходит за гарантии протокола. Общая модель: [e2e-threat-model.md](e2e-threat-model.md).

Новые таблицы `device_sessions`, `device_pairings`, `device_pair_limits` создаются штатным `Base.metadata.create_all` при старте сервера; колонки `device_sessions.e2e_public_key` и `e2e_reported_at` добавляются при старте через `ALTER TABLE … ADD COLUMN IF NOT EXISTS`. Новых переменных окружения не требуется. HTTPS и корректный доверенный reverse proxy обязательны для production. Периодическая задача очищает просроченные зашифрованные пакеты, старые запросы и счётчики; записи отозванных сеансов сохраняются до истечения JWT.

## Проверки

Backend: `python -B -m unittest tests.test_device_pairing` из `backend`, с `TEST_DATABASE_URL` на тестовую PostgreSQL. Suite пересоздаёт схему `quazar_test`; не запускайте несколько таких suite одновременно.

Web: `npm test` и `npm run build` из `web`.

Сквозная проверка: сначала соберите `web` и установите зависимости `desktop`, затем из корня запустите `backend/.venv/bin/python -B desktop/test/run-device-pairing.py`. `TEST_DATABASE_URL` должен указывать на локальную PostgreSQL с правом создания временной БД. Harness создаёт и удаляет отдельную БД, синтетический аккаунт и четыре изолированных профиля Chromium; внешние запросы заблокированы. Проверяет код, QR в обе стороны, реальное декодирование отображённого QR, совпадение перенесённого seed, разные сеансы и их отзыв. С `BROWSER_TEST_CASE=key-transfer` проверяется перенос ключей на устройства, где уже вошли: через всплывающее предложение и по коду из настроек, с цепочкой передачи и неизменными сеансами. На Linux нужен `xvfb-run -a`. В CI эти проверки обязательны перед десктопной сборкой.
